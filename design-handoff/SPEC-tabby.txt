

# Spec: Tabby (SWH Test App)
2026-10-19 · 
Spec นี้กำหนดแอป CRUD เล็กๆ ที่เขียนซ้ำ 4 เวอร์ชัน (Apache, Nginx, Node, Python) โดยใช้ฐานข้อมูล, API และหน้าเว็บชุดเดียวกัน เพื่อวัดว่า Shared Web Hosting (SWH) ของ Dimenshade รันแต่ละ stack ได้ถูกต้องและเร็วแค่ไหน

## 1. ภาพรวมและวัตถุประสงค์
แอปชื่อ "Tabby" (สมุดจดหนี้เพื่อน) ใช้จดว่าเพื่อนคนไหนยืมเงินเท่าไร ตัวแอปตั้งใจให้ง่ายที่สุด เพราะสิ่งที่ต้องทดสอบคือตัว hosting ไม่ใช่ตัวแอป
เป้าหมาย
- 
ตรวจว่า SWH รัน PHP บน Apache, PHP บน Nginx, Node.js และ Python ได้ครบ ทั้งการเชื่อมต่อ DB, สิทธิ์ไฟล์, SSL และ log
- 
วัด bandwidth, caching และ API request ด้วย endpoint ชุดเดียวกันในทุก stack เพื่อเทียบกันตรงๆ
- 
หาจุดที่ account ถูกจำกัด (CPU, RAM, I/O, bandwidth, จำนวน process) ก่อนเปิดให้ลูกค้าใช้จริง
- 
ได้โค้ดชุดเดียวที่อัปโหลดแล้วทดสอบซ้ำได้ทุกครั้งที่ปรับ config
ไม่อยู่ในขอบเขต
- 
ระบบล็อกอินและสิทธิ์หลายระดับ
- 
UI สวยงามหรือฟีเจอร์ธุรกิจจริง
- 
Stress test ระดับ production ที่กระทบ account อื่นบนเครื่องเดียวกัน
- 
การตั้งค่าระดับ server ที่ทำนอกแผงควบคุมของ SWH
ถือว่าสำเร็จเมื่อ
- 
ทั้ง 4 เวอร์ชันผ่าน CRUD ครบ 5 operation (list, read, create, update, delete)
- 
ทั้ง 4 เวอร์ชันผ่านทุกข้อที่เป็น "ต้องผ่าน" ในหัวข้อ 11 หรือมีบันทึกสาเหตุที่ไม่ผ่านพร้อมแนวทางแก้ และมีผลครบทุกข้อที่เป็น "บันทึกผล"
- 
มีตารางผลเปรียบเทียบ 4 stack หนึ่งตาราง

## 9. แนวทางเขียนแต่ละ Stack
ทุก stack ต้องให้ผลตามหัวข้อ 4 ถึง 8 ทุกประการ ส่วนวิธีเขียนเป็นอิสระ ตราบที่ไม่ผิดข้อกำหนดด้านล่าง
ส่วนที่เหมือนกันทุก stack
- 
ไฟล์หน้าเว็บ (index.html, test.html, app.js, style.css) เป็นไฟล์เดียวกัน byte ต่อ byte
- 
ค่าเชื่อมต่อ DB อยู่ในไฟล์ config หรือ environment ที่อยู่นอก document root ห้ามอยู่ในไฟล์ที่เปิดผ่านเว็บได้
- 
ทุก connection ตั้ง time zone เป็น +00:00 และใช้ prepared statement
- 
ขนาดไฟล์ที่ /upload รายงานเป็นขนาดของไฟล์ในช่อง file เท่านั้น ไม่รวมส่วนหัว multipart ยอมให้คลาดเคลื่อนไม่เกิน 1%
Apache + PHP
- 
ทางเข้าเดียวคือ index.php และไฟล์ .htaccess ส่งทุก request ที่ไม่ใช่ไฟล์จริงไปที่ index.php (ต้องเปิด mod_rewrite และ AllowOverride)
- 
DB ใช้ PDO MySQL
- 
/download อ่านและส่งทีละ 64 KB พร้อม flush() ปิด output buffering ก่อน และตรวจว่า max_execution_time ไม่ตัดการส่งไฟล์ 100 MB
- 
/upload อ่านขนาดจาก $_FILES ผลจะถูกจำกัดด้วย upload_max_filesize และ post_max_size ให้จดค่าที่พบ
- 
PUT และ DELETE อ่าน body จาก php://input
- 
ห้ามเปิด ob_gzhandler ในโค้ด ให้ mod_deflate ของ server ทำหน้าที่บีบอัด
Nginx + PHP-FPM
- 
ใช้โค้ด PHP ชุดเดียวกับเวอร์ชัน Apache ไม่แก้โค้ด เปลี่ยนเฉพาะ routing
- 
Nginx ไม่อ่าน .htaccess จึงต้องตั้ง try_files $uri /index.php?$query_string; ผ่านช่องทางที่ SWH เปิดให้ปรับ config ของโดเมน ถ้า SWH ไม่เปิดให้ปรับ ให้บันทึกเป็นข้อจำกัด
- 
ถ้า SWH ใช้ Nginx เป็น reverse proxy หน้า Apache จะใช้ .htaccess ได้เหมือนเดิม ให้จดโหมดที่พบ
- 
ให้ PHP ส่ง header X-Accel-Buffering: no ใน /download เพื่อให้ Nginx ส่งแบบ stream
- 
ค่าที่ต้องจด: client_max_body_size (กระทบ /upload), fastcgi_read_timeout (กระทบ /api/slow)
Node + Express
- 
ทางเข้า app.js อ่านพอร์ตจาก environment variable PORT
- 
DB ใช้ mysql2 แบบ connection pool (ขนาด 5)
- 
/download ใช้ res.write ทีละ 64 KB และรอสัญญาณ drain ก่อนเขียนต่อ ห้ามสะสมในหน่วยความจำ
- 
/upload นับ byte จาก stream โดยไม่เก็บลงดิสก์ (เช่น busboy)
- 
เปิด trust proxy เฉพาะเมื่อยืนยันแล้วว่าอยู่หลัง proxy ของ SWH เพื่อให้ client_ip ถูก
- 
ไฟล์ static ใช้ express.static (มี ETag ให้โดยค่าเริ่มต้น)
- 
ต้องหาวิธี start, stop และ restart แอปบน SWH ให้ได้ และจดเวลาที่แอปกลับมาตอบหลัง restart
Python + Flask
- 
ทางเข้า app.py ที่เปิด object application สำหรับ WSGI (ถ้าใช้ Passenger ให้ตั้ง passenger_wsgi.py ชี้มาที่ตัวนี้)
- 
DB ใช้ PyMySQL (หรือ driver อื่นที่ใช้ได้บน SWH)
- 
/download ใช้ generator ที่ส่งทีละ 64 KB ผ่าน Response แบบ stream
- 
/upload ต้องไม่เก็บไฟล์ลงดิสก์ถาวร และรายงานเฉพาะขนาดไฟล์ตามข้อกำหนดข้างต้น
- 
จำนวน worker และ thread ของ WSGI กำหนดว่า /api/slow รับ request พร้อมกันได้กี่ตัว ให้จดค่าที่ SWH ตั้งไว้
- 
ใช้ virtualenv ของ account และจด dependency ใน requirements.txt

## 11. แผนทดสอบและเกณฑ์ผ่าน
ทดสอบทีละ stack ตามลำดับ ทำงานเชิงฟังก์ชันก่อน ตามด้วย caching, API request และจบด้วย bandwidth ที่กินโควตามากที่สุด เกณฑ์ตัวเลขด้านล่างเป็นค่าเริ่มต้นที่เสนอ ให้ปรับหลังได้ผล baseline รอบแรก

-

-

Endpoint ทดสอบกินทรัพยากรหนัก (ไฟล์ 100 MB, หน่วง 10 วินาที, seed 10,000 แถว) บน shared hosting อาจกระทบ account อื่นหรือโดนระบบจำกัดการใช้งาน จึงต้องมีตัวกั้นและเพดานในตัวแอป
ตัวกั้นด้วย token
Endpoint ที่หนักต้องส่ง header X-Test-Token ที่ตรงกับ TEST_TOKEN ในไฟล์ config (เปรียบเทียบแบบ constant-time) ถ้าไม่ตรงหรือไม่ส่งมา ตอบ 403 {"error": "forbidden"} หน้า /test มีช่องกรอก token และเก็บไว้ในหน่วยความจำของหน้านั้นเท่านั้น

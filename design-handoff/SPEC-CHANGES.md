## 1. `/api/summary` เพิ่ม field `count_friends_unpaid` / `/api/summary` gains `count_friends_unpaid`

ใส่ใน §5 ตรง `/api/summary`

- ชนิด: integer
- นิยาม: จำนวนชื่อเพื่อนที่ไม่ซ้ำกันของรายการที่ยังไม่จ่าย ใน SQL คือ `COUNT(DISTINCT CASE WHEN is_paid = 0 THEN LOWER(friend_name) COLLATE utf8mb4_bin END)`
- ตัวอย่าง: เพื่อนชื่อเดียวกันมีหนี้ที่ยังไม่จ่าย 2 แถว นับเป็น 1
- การเทียบชื่อไม่แยกตัวพิมพ์เล็กใหญ่ (`Ann` กับ `ann` นับเป็นคนเดียวกัน) แต่แยกวรรณยุกต์ไทยและ emoji (`ป้า` กับ `ปา` เป็นคนละคน) โดยใช้ `LOWER(...) COLLATE utf8mb4_bin` เพราะ `utf8mb4_unicode_ci` มองว่า `ป้า`=`ปา`, `กา`=`ก่า` และ emoji ต่างตัวเท่ากัน ทำให้นับเพื่อนต่ำกว่าจริง

ตัวอย่าง response ฉบับเต็ม (`200 OK`, header `X-App-Cache: HIT` หรือ `MISS`):

```json
{
  "total_unpaid": "12345.00",
  "count_unpaid": 7,
  "count_paid": 3,
  "count_all": 10,
  "count_friends_unpaid": 4,
  "generated_at": "2026-10-21T10:00:00Z"
}
```

| field | ชนิด | ความหมาย |
|---|---|---|
| `total_unpaid` | string | ผลรวม `amount` ของแถว `is_paid = 0` ทศนิยม 2 ตำแหน่งเสมอ ไม่มีแถวคือ `"0.00"` |
| `count_unpaid` | integer | จำนวนแถวที่ `is_paid = 0` |
| `count_paid` | integer | จำนวนแถวที่ `is_paid = 1` |
| `count_all` | integer | จำนวนแถวทั้งหมด |
| `count_friends_unpaid` | integer | จำนวนชื่อเพื่อนไม่ซ้ำที่ยังมีหนี้ค้าง (ใหม่) |
| `generated_at` | string | เวลา UTC ที่คำนวณค่า ในรูป ISO 8601 ลงท้าย `Z` ตอบ HIT จะเป็นเวลาของครั้งที่คำนวณ ไม่ใช่เวลาปัจจุบัน |

## 2. ตารางข้อความ validation / Validation message table

ใส่ใน §5 ใต้ `POST /api/debts` และ `PUT /api/debts/{id}` (ใช้กฎชุดเดียวกัน) ข้อความเป็นภาษาไทยและต้องตรงทุกตัวอักษร

Response เมื่อไม่ผ่าน: `422` กับ `{"error": "validation_failed", "fields": {"<field>": "<ข้อความ>"}}` โดยรายงานทุก field ที่ผิดพร้อมกัน

| Field | ข้อความ | เงื่อนไขที่ทำให้เกิด |
|---|---|---|
| `friend_name` | `ห้ามว่าง` | ไม่ส่งมา, ไม่ใช่ string, หรือว่างหลัง trim |
| `friend_name` | `ยาวเกิน 100 ตัวอักษร` | เกิน 100 ตัวอักษร (นับเป็นตัวอักษร ไม่ใช่ byte) หลัง trim |
| `amount` | `ต้องเป็นตัวเลข` | ไม่ส่งมา, `null`, boolean, ไม่ใช่ตัวเลขทศนิยมธรรมดา (`1e3`, `1,000`, `.5`, `150.`, `abc` ไม่ผ่าน), หรือเป็น JSON number ที่แปลงแล้วออกมาเป็นรูป exponent / ค่าอนันต์ (เช่น `1e25`, `1e999`) |
| `amount` | `ต้องมากกว่า 0` | ค่าติดลบ หรือเท่ากับศูนย์ (`0`, `0.00`) |
| `amount` | `ทศนิยมไม่เกิน 2 ตำแหน่ง` | มีทศนิยมเกิน 2 หลัก **นับจากจำนวนหลักตรงๆ** ดังนั้น `"1.500"` ถูกปฏิเสธ แม้ค่าจะเท่ากับ `1.5` และ `"1.005"`, `"0.001"` ก็ไม่ผ่าน |
| `amount` | `ต้องไม่เกิน 99,999,999.99` | ส่วนจำนวนเต็มเกิน 8 หลัก (หลังตัดศูนย์นำหน้า) |
| `note` | `ต้องเป็นข้อความ` | ส่งมาแต่ไม่ใช่ string และไม่ใช่ `null` |
| `note` | `ยาวเกิน 255 ตัวอักษร` | เกิน 255 ตัวอักษร หลัง trim |
| `is_paid` | `ต้องเป็น 0 หรือ 1` | ส่งมาแต่ไม่ใช่ `0`, `1`, `true`, `false` (`"1"`, `2`, `null` ไม่ผ่าน) |

หมายเหตุประกอบตาราง

- `amount` รับ number หรือ string แล้วเทียบเป็นสตริงตัวเลข ไม่แปลงเป็น float จึงไม่มีปัญหาปัดเศษ JSON number ที่ผู้ส่งเขียนเป็น `1.001` ถูกปฏิเสธด้วย `ทศนิยมไม่เกิน 2 ตำแหน่ง` เช่นเดียวกับ string `"1.001"`
- ลำดับตรวจ `amount`: รูปแบบตัวเลข, แล้ว `มากกว่า 0`, แล้วทศนิยม, แล้วค่าสูงสุด ตัวอย่าง `"99999999.991"` ได้ข้อความเรื่องทศนิยม
- ค่า `amount` ที่ผ่านจะถูก normalize เป็นทศนิยม 2 ตำแหน่งเสมอ (`" 150 "` -> `"150.00"`, `"007"` -> `"7.00"`)
- `is_paid` ไม่ส่งมาถือเป็น `0` (PUT เป็น full replacement จึงรีเซ็ตเป็น `0` ถ้าไม่ส่ง)
- Body ที่ไม่ใช่ JSON object (`[]`, `[1]`, `"x"`, ว่าง, JSON เสีย) ตอบ `400 {"error": "invalid_json"}` ส่วน object ที่ key เป็นตัวเลข เช่น `{"0":1}` ยังเป็น object ต้องผ่านการ validate ได้ `422`

## 3. พฤติกรรมที่ทุก stack ต้องเหมือนกัน / Cross-stack behavior

ใส่ใน §5 (หรือหัวข้อกติกากลางของ API) เพื่อให้ nginx / node / python ทำตรงกับ apache

1. **PUT ตรวจ body ก่อนตรวจว่ามีแถวหรือไม่ / PUT validates before existence.** ลำดับคือ parse body (400) -> validate (422) -> หาแถว (404) ดังนั้น `PUT /api/debts/{id}` ที่ id ไม่มีอยู่ แต่ body ไม่ผ่าน validation ต้องตอบ `422` ไม่ใช่ `404`
2. **`note` ถูก trim ก่อนตรวจความยาวและก่อนเก็บ / note is trimmed.** ช่องว่างหัวท้ายถูกตัดก่อนเทียบเพดาน 255 ตัวอักษร และค่าที่เก็บลง DB และตอบกลับคือค่าที่ trim แล้ว
3. **`note` ว่างหลัง trim เก็บเป็น `null` / empty note becomes null.** ส่ง `""` หรือ `"   "` มา ผลคือ `note: null` (ไม่ใช่สตริงว่าง)
4. `friend_name` ถูก trim ก่อนตรวจและก่อนเก็บเช่นเดียวกัน

## 4. Table options ของ schema / Schema table options (§3)

ใส่ใน §3 ว่าทุกตาราง (`debts`, `rate_limits`) ต้องประกาศ option ต่อไปนี้ชัดเจนท้าย `CREATE TABLE`:

```sql
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

เหตุผล: ค่า default ของ MySQL บน shared hosting (SWH) บางแห่งยังเป็น `latin1` ซึ่งทำให้ข้อความภาษาไทยเสียหายเมื่อบันทึก (กลายเป็น `?` หรือ mojibake) การระบุ charset และ collation เองทำให้ผลเหมือนกันทุกเครื่อง ส่วน `count_friends_unpaid` (ข้อ 1) ไม่พึ่ง collation ของตาราง แต่เทียบด้วย `LOWER(friend_name) COLLATE utf8mb4_bin` เพื่อให้ไม่แยกตัวพิมพ์เล็กใหญ่ แต่แยกวรรณยุกต์ไทยและ emoji การเชื่อมต่อฝั่งแอปใช้ `charset=utf8mb4` ตรงกัน

นี่เป็นการเบี่ยงจาก Spec §3 เดิมที่ไม่ได้ระบุ option เหล่านี้ (ระบุไว้เป็นคอมเมนต์บรรทัดแรกของ `shared/schema.sql` แล้ว)
